# Phase F1 checkpoint — guided setup and usage controls

Approved and implemented on 2026-09-24. This is a core milestone, not a production release or a claim of zero wasted tokens. F2 project migration/docs retrieval and F3 local coding/independent review have not started.

## Delivered

- Daemon-owned, resumable four-step setup: purpose and usage preferences, supported harness/account checks, local model guidance and a final summary. Standard cards work before installing any model. Reopen setup from the workspace. Preferences use a separate transactional local SQLite store with revision checks; this is installation configuration, not a thread event projection. Existing event semantics are unchanged.
- Local, subscription-only and explicitly authorized paid usage modes. Cloud dispatch checks apply at the shared delivery path, including warm follow-ups, planner/implementation/repair, crash recovery and rate-limit retry. Setup changes stop active harnesses; work and session IDs remain available. Admission is serialized against settings changes and concurrent launches. Plan scheduling respects the installation concurrency limit and waits for slots.
- Read-only CLI status discovery: Claude `auth status`, Codex app-server `account/read` and `account/rateLimits/read`, plus CLI versions. Only sanitized account type/plan, usage windows/reset times, credit availability, source and observation time reach the API. No prompts, credit purchases or reset redemption. Unsupported/partial/failed status stays unknown.
- Subscription mode blocks API authentication, conflicting API/provider environment, unknown or enabled extra credits, missing/expired quota windows, and usage at or above 90%. Status expires after 120 seconds. Refreshes are coalesced and limited to once per 30 seconds; completed cloud-enabled installations refresh read-only status every minute. The 10% headroom is a conservative admission rule, not a reservation at the provider or an exact billing cap.
- Paid mode requires explicit consent and permits reported API authentication. It does not silently activate when subscription mode is blocked. Codex subscription launches request ChatGPT authentication and the OpenAI provider explicitly. Credentials remain managed by the official harness.
- CPU, OS, architecture, physical memory and available model-disk capacity (best effort, OS code in supervisor). Hardware guidance starts with the small classifier, then optional benchmarked question models. Download actions check disk headroom. Model installation retains pinned checksums, adds cancellation and HTTP-range resume of partial files, and requires a benchmark before selecting a question model. Disabling network downloads cancels owned downloads. No model weights were downloaded during this implementation's verification.
- New-task and follow-up model/effort/access/tool controls are under Advanced. Thread cost/model/memory diagnostics are under Task details. Default subscription plan summaries hide the misleading dollar threshold. Codex cost is labeled unavailable; cost dialogs explain that reported values are not subscription allowance and thresholds can overshoot.
- Responsive project-add form, setup headings focused after step changes, inline errors, a visible model-dialog close action, and disabled controls during setup mutations.

## Explicit limits and remaining acceptance

- Harness installation/sign-in currently uses guided official documentation links and CLI commands. Arbiter does not yet execute installers or embed an OAuth wizard. Fresh-machine installer failure/rollback and interactive sign-in remain manual acceptance checks.
- Native read-only verification: Claude Code 2.1.278 and Codex 0.154.0 reported subscription authentication. Codex returned live usage windows and `credits_enabled: false`. Claude's documented auth-status output did not supply quota or extra-credit settings, so protected Claude execution remains blocked. An earlier restricted preview could not read Codex status; restarting the isolated daemon with native CLI access resolved that environmental limitation. No real coding inference was used; quota discovery is not an end-to-end provider coding acceptance run.
- Extra-credit availability is only evidence returned by the provider, not control over billing settings. Other clients, account changes, custom harness configurations and in-flight work can invalidate a snapshot. There is no provider-enforced exact dollar cap or guarantee of zero consumed/wasted quota. Unknown status deliberately blocks protected cloud use.
- Cloud-off mode disables Arbiter's coding-agent launches. The network preference gates status queries/model downloads; it is explicitly not an OS-level network sandbox for arbitrary project scripts or browser tools. Strict offline containment remains a release requirement before advertising full offline isolation.
- Local models currently assist intake/questions. A local coding executor and documentation-backed second opinion remain F3, with documentation profiles/retrieval in F2. A workspace can be configured while cloud execution remains blocked; the UI must not imply that local coding is ready.
- RAM/disk detection is best effort; GPU-specific recommendations, broad hardware benchmarks, macOS/Linux runtime acceptance and native 200% zoom/accessibility coverage remain open. Existing C latency and E real-provider savings gates remain open.

## Design reconciliation

The existing palette, fonts, shared primitives and scroll ownership are retained. Progressive disclosure is the intentional change: setup owns account policy/model preparation, the composer emphasizes the user's task, and advanced controls remain reachable. No visual token changes.
